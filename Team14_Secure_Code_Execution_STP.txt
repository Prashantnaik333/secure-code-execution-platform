1. Introduction
1.1 Purpose
This plan defines the test scope, strategy, environment, test cases, responsibilities, schedule, risks, and acceptance criteria for Team 14's Secure Online Code Execution Platform.
1.2 Scope
Testing covers input validation, job submission and status, isolated execution, output/error capture, time/resource limits, authorization where implemented, cleanup, health checks, logging safety, and CI workflow. Use controlled test programs in a non-production environment.

4. Features Not to be Tested
Security certification or proof of immunity to all possible sandbox escapes.
Production-scale load testing without a production-like environment.
Compiler/runtime correctness beyond supported examples and error handling.
External identity providers, cloud infrastructure, or third-party integrations not implemented.
5. Test Approach / Strategy
5.1 Levels
Unit tests: input validation, state transitions, error formatting, output-size handling.
Integration tests: API to job manager, worker invocation, result persistence, and cleanup.
System tests: end-to-end submission, execution, and result display.
Security tests: controlled attempts to exceed limits, read prohibited files, access another job, or use blocked network access.
CI tests: verify tests run automatically on pull requests and main updates.
5.2 Entry and Exit Criteria
Entry: runnable build available; isolated test environment ready; supported languages and limits documented; test programs ready.
Exit: all planned critical/high-priority tests executed; critical security tests pass; no open critical defects; RTM updated; CI passes.
5.3 Security Validation
Verify code is not executed in the privileged API process.
Verify timeout/resource exhaustion is contained.
Verify sandbox cannot access protected host test files or secrets.
Verify network access is blocked by default where configured.
Verify users cannot retrieve jobs they do not own, if ownership/authentication is implemented.
Verify logs and errors do not disclose secrets or stack traces.

10. Risks and Mitigation
Risk
Mitigation
Sandbox differs across hosts
Document environment and test exact deployment configuration.
Resource-limit test hangs
Use conservative limits, an outer test timeout, and a disposable VM/container.
Feature merges break another module
Require CI, one approval, and regression tests for every PR.
Deadline is close
Work in parallel on independent sections and merge small reviewed PRs early.
Missing numeric limits or language scope
Record explicit values and versions before acceptance.
Tests are nondeterministic
Use bounded programs and a repeatable environment setup.
11. Assumptions and Dependencies
The team repository is accessible to all four members.
The chosen execution environment supports intended isolation/resource controls.
Compiler/runtime packages are available in the test environment.
CI is enabled for the team repository.
The team agrees on the stack and numerical limits.
12. Suspension and Resumption Criteria
Suspend security/resource tests if the environment becomes unstable, host impact is suspected, or a test process cannot be reliably terminated. Resume after the environment is restored, leftover processes are cleaned up, and the test owner confirms safe conditions.
