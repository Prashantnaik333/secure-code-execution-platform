1. Introduction
1.1 Purpose
This SRS defines the functional, non-functional, interface, security, and acceptance requirements for a Secure Online Code Execution Platform. It is the baseline for implementation, testing, and evaluation.
1.2 Scope
The platform allows a user to submit source code in supported languages, execute it in an isolated runtime, enforce execution and resource limits, and view standard output, standard error, exit status, and execution metadata. The platform must prevent submitted programs from accessing host files, secrets, other users' jobs, or unrestricted network resources.
1.3 Audience
Student developers, testers, project evaluator, maintainers, and users of the platform.
1.4 Definitions
Sandbox: restricted execution environment; Job: one submitted program execution; stdout: standard output; stderr: standard error; CPU limit: maximum processor time; wall-clock timeout: maximum elapsed time; RBAC: role-based access control; CI: continuous integration.
2. Overall Description
2.1 Product Perspective
A web-based application composed of a user interface, API/backend, job queue or job manager, isolated execution worker, and persistent metadata store. The execution worker is treated as an untrusted-code boundary and must not run submitted code with application/server privileges.
2.2 Product Functions
Write or paste code in an editor and select a supported programming language.
Submit code with optional standard input and receive a job identifier.
Compile code when required and execute it in a sandbox.
Enforce wall-clock timeout, CPU/memory limits, and output-size limits.
Capture stdout, stderr, compile errors, exit code, and execution duration.
Show job states: queued, running, completed, failed, timed out, or rejected.
Reject unsupported languages, malformed requests, and oversized submissions.
Isolate jobs from one another and restrict filesystem and network access.
Provide basic health/status information and operational logs without storing secrets or unnecessary source data.
Run automated tests in CI and require reviewed changes before merging to main.
2.3 User Roles
User: submits and views their own code execution jobs.
Maintainer/administrator: configures supported languages and limits, monitors service health, and reviews security logs.
Developer/tester: develops features on separate branches and validates changes with automated tests.
2.4 Operating Environment
Modern desktop/mobile browser; backend service on a Linux-capable host; isolated worker runtime using OS-level sandboxing such as containers with restrictive security settings. Exact deployment platform and supported languages must be confirmed by the team.
2.5 Constraints and Assumptions
Submitted code is untrusted and must never execute directly inside the privileged web/API process.
Execution requires strict default-deny resource and permission settings.
A finite list of languages and compiler/runtime versions will be maintained.
The initial project may use a local or educational deployment; production-grade multi-tenant security requires additional review.
The service must fail safely if the worker is unavailable or a job exceeds limits.
3. External Interface Requirements
3.1 User Interface
Code editor, language selector, optional stdin field, Run button, and clear validation messages.
Execution result panel displaying stdout, stderr, compile errors, status, exit code, and duration.
Show timeout/resource-limit failures in a readable form without exposing internal paths or secrets.
3.2 Software Interfaces
Frontend-to-backend HTTPS/HTTP API according to deployment environment.
Backend-to-worker interface that passes a job payload and receives bounded result metadata.
Persistent store for job metadata where implemented; do not store secrets or full output indefinitely by default.

3.4 Input and Output Limits
The implementation must define configurable maximum source size, stdin size, output size, memory, CPU time, and wall-clock duration. Initial numeric values must be documented in configuration and tests before acceptance; do not treat unspecified values as unlimited.

5.1 Security Objectives
Confidentiality: users cannot read other users' code/results or access host secrets through submitted programs.
Integrity and availability: submitted programs cannot modify host/application data or consume unbounded resources to disrupt the service.

6. Quality Attributes and Acceptance Tests
All critical and high-priority requirements must have corresponding tests.
All critical security tests must pass before demonstration or release.
No open critical defect may remain at acceptance.
CI must pass and the pull request must receive at least one teammate approval before merge.
Numeric resource defaults and supported language versions must be recorded in configuration and test documentation.
