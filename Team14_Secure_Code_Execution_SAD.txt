1. Introduction
1.1 Purpose
This document describes the architecture, components, security boundaries, interfaces, and design decisions for the Secure Online Code Execution Platform.
1.2 Scope
Covers code submission, validation, job management, isolated compilation/execution, output capture, limit enforcement, result retrieval, logging, and CI workflow.
1.3 Audience
Developers, testers, maintainers, and project evaluators.
1.4 Definitions
API, sandbox, worker, job queue, stdout, stderr, CPU quota, memory limit, wall-clock timeout, CI, PR.

3. Architecture
3.1 Goals and Constraints
Run user-submitted code without trusting it.
Apply independent limits for time, memory, CPU, and output.
Keep UI/API separate from untrusted execution.
Provide clear results and safe failure behavior.
Support testable modules and reviewed changes through branch/PR/CI workflow.

3.5 Chosen Architecture Pattern and Rationale
Use a layered architecture with a separate execution-worker boundary. Presentation, API/validation, job orchestration, execution, and persistence are separated for testability and security. Submitted code must not run inside the privileged web process. A microservices deployment is not required for the initial academic scope, but the worker isolation boundary remains mandatory.

3.9 Security Architecture
Treat source code, stdin, generated files, and program output as untrusted.
Validate inputs and enforce language allowlists.
Run each job with least privilege, bounded resources, isolated temporary storage, and no unnecessary network access.
Never mount host credentials, Docker socket, home directories, or sensitive application files into the sandbox.
Apply authorization checks to result retrieval.
Avoid exposing stack traces, secrets, environment variables, or internal paths.
Clean up child processes and temporary files on success, error, timeout, and cancellation.
4. Design
4.1 Design Overview
Normal flow: user submits code → API validates request → job manager creates job → worker starts isolated sandbox → compiler/runtime executes under limits → worker captures bounded results and cleans up → API returns status and result to authorized user.

4.4 Error Handling, Logging and Monitoring
Use structured categories: validation, unsupported language, compile failure, runtime failure, timeout, resource limit, unauthorized access, and internal failure.
Return safe messages to users; keep detailed diagnostics in restricted logs.
Record timestamps, job ID, lifecycle status, duration, and failure category without secrets.
Expose readiness for the API and execution worker.
Ensure cleanup runs even when execution fails.
4.5 UX Design
Keep Run and language selection visible; show a running state while a job executes.
Distinguish compilation errors from runtime errors and timeouts.
Display stdout and stderr separately and indicate truncated output.
Do not report success if the worker failed or a timeout occurred.
